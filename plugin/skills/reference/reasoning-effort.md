# Per-task reasoning effort and evidence (read on demand)

Applies to Boost, Teamwork and Swarm alike. Read it before the first spawn of a run, and whenever you spawn a role whose task differs in difficulty from earlier ones.

1. **Choose before first spawn**, for authors, verifiers, planners, challengers and read-only helpers. Start at `medium` for bounded evidence or contract checks; choose `high` for cross-module investigation, consistency work or a critical independent review. Use `ultra` only when the particular task warrants deeper reasoning than `high`; neither the parent tier, the size of the project nor workflow `complexity` is a reason on its own. Prefer `fork_turns="none"` with the selected effort when the live schema and resolved model support it. Use `fork_turns="all"` only when reusing context is needed and the role allows it; omit both override parameters and record why.
2. **Freeze the plan with the dispatch.** Record it structurally first: `workflow_prepare_dispatch(options={"effort_plan": {...}})` or `worker_register(effort_plan={...})` with `target_effort`, `selection_reason`, `planned_source` and optional `override_unavailable_reason`; the dashboard shows it next to the worker. For a child without a worker record, append `target_effort`, `selection_reason`, `planned_source` and, if the target cannot be sent or a known role override supersedes it, `override_unavailable_reason` to the existing ticket `body_md` without replacing the task instructions. For an already-prepared ticket or a child with no ticket, use a `board_post` on `main` before spawning, keyed by the native task path (and step/message IDs when available). The planned source is `explicit`, `role_override`, `agents_default`, `model_default`, `session_inheritance` or `unknown`. Check the [native configuration precedence](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents): a configured role effort supersedes the argument; before that override the host resolves explicit effort, `[agents]` effort, and model default or parent effort. If settings cannot be verified, use `unknown` rather than claiming inheritance. Record the exact reason for omitting the argument.
3. **Observe independently after spawn.** Pass the observation as `native_action_record_call(observed_effort={observed_effort, observed_source, evidence_ref, evidence_kind, codex_thread_id})` when you have it (otherwise link a `main` board note to the plan) and record the matched child `codex_thread_id`, `observed_effort`, `observed_source`, and `evidence_ref`. Prefer the first turn belonging to the child in its Codex rollout (ignore copied parent turns). If checking the bound child in the session catalog or run worker view, record it as a catalog snapshot and do not treat a later turn's value as the first turn. Resolve the source from the actual spawn arguments and known host configuration, not just an equal numeric/tier value. A spawn receipt or a parent setting alone is not child evidence. If first-turn evidence is missing, use `unverified`; if the tier is observed but the source is not established, use `unknown`. Retain mismatches and different models as observed, not as successful same-model routing. This record does not change verification gates; same-thread `followup_task` has no new spawn override.
