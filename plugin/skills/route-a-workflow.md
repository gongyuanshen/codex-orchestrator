# Route A structured workflow (new workflow4; stored workflow_version=1/2/3/4)

Load this shared contract before executing Boost, Teamwork or Swarm. Existing migrated version0 runs retain their historical contract and are labeled legacy. Stored workflow1 retains its foundation contract; workflow2 adds the mode-specific bindings below; workflow3 adds the M2 collector. New runs use workflow4 (software 0.5.0/schema7), inheriting all prior gates, controls and budgets plus M3 plan admission/handoff/review and M5 grouped transfers. Stored workflow0/1/2/3 semantics never change or acquire fabricated evidence. Unknown versions are unsupported; no public downgrade selector. Never use raw SQL, metadata, worker status or a board PASS to disable gates. A receipt is not independent acceptance.

## Coordinator: frozen work and native dispatch

1. Freeze the verbatim requirement and nonempty unique string acceptance criteria with task_packet_save. Spawn actual author and verifier agents; register their exact native agent_id values. They must be a different native agent, not merely different names. Solo uses the actual coordinator as the author and a separate native verifier.
2. Create a work item with workflow_step_save(run_id,step_key,owner,verifier,workspace_id when used,dependencies,criteria). Criteria must cover the frozen packet across the mandatory work items. Do not weaken criteria to bypass a failure. Keep the returned step id/revision; every workflow_step_advance requires expected_revision from a fresh stored step.
3. Call workflow_step_advance(action="dispatch") before native implementation dispatch, after registering real native bindings; bootstrap children remain waiting-only and must not implement early. Persist the admitted business message with inbox_send before any native wakeup, then follow the M1 native transfer ledger sequence below. Admission and persistence do not prove host execution.
4. An idle/ended child is resumed only through the actual native followup_task/send_input. A working child can receive native send_message at the host's supported boundary. Honor pending controls first; never resume paused/killed workers automatically. Use action="observe" only after an actual native observation, passing observation={agent_id,state,observed_at,evidence}; heartbeat is not host telemetry.

## M1 native transfer ledger

Candidate software 0.4.0/schema6 adds a transfer ledger; workflow0/1/2 semantics remain unchanged. The M1 ledger itself introduces no workflow3 business gate; the M2 section below defines that additive contract. This protocol applies to transfers through the additive M1 interface, not retroactive evidence for historical runs. Bootstrap children are waiting-only until admission and persisted delivery.

1. Persist admitted business work with inbox_send using a stable work-item/attempt key and step_id before waking the original author or original verifier. Rework retains both original identities and the existing maximum 3 automatic rework rounds; no new packet/name/route resets that budget.
2. Query board_status and inspect bounded next_actions, needs_reconciliation, needs_clarification and truncation/count metadata. Querying is read-only: it does not ACK, claim, expire leases, advance cursors or dispatch. Handle pending controls before business wakeups; a projection is not fresh authorization.
3. Call native_action_update(action="claim") using the projected run_id, source_type (inbox|control|human), source_id string, recipient, action_type (followup_task|send_message|interrupt_agent) and source_digest. Use persisted source context, not reconstructed free text. Claim rechecks current version, attempt, binding and controls, returning action_id, claim_token, lease deadline and revision.
4. Call native_action_update(action="begin") with action_id, claim_token and expected_revision from claim. Begin rechecks freshness and controls immediately before marking invoking. Do not invoke if claim/begin fails. Use the returned revision for the subsequent record.
5. Make the actual native call against the original bound target, with the persisted payload: followup_task for idle/ended, send_message for working, interrupt_agent for the exact control target. The daemon never invokes the host. Observe the actual tool result; a heartbeat, SSE or shared MCP identity is not native takeover or authentication.
6. Call native_action_update(action="record") with action_id, claim_token, expected_revision, outcome (confirmed|failed|not_called|rejected|unknown), evidence_ref, lowercase SHA256 evidence_digest and nonblank result for the actual host result. Ledger confirmation proves transfer only: inbox ACK, business PASS and control ACK are separate. After confirmed interruption, worker_control_ack still records the actual applied/failed control outcome; do not synthesize it from ledger state.

Lease expiry, restart, disconnect or lost results after begin require needs_reconciliation: never automatically replay an unknown action or use an expired token. Use native_action_update(action="reconcile") with current action_id/expected_revision and retained host evidence; timeout alone is not proof of non-execution. Only evidenced outcome="not_called" (known non-invocation) or outcome="rejected" (explicit host rejection) permits another claim; generic failed does not. Reconcile uses the same outcome/evidence/result fields, only on needs_reconciliation rows, without an old claim token. Unknown stays fenced. Keep original failed/uncertain evidence. No automatic resume of paused/stopped/killed members. A stop racing an already-issued call requires recording the race and real interruption, not claiming instant cancellation. SQLite and the host share no transaction: this is not exactly-once execution.

Controls retain the original control_request_id as source_id; human guidance retains the original seq (encoded as source_id string) and verbatim text. Resolve one registered recipient; ambiguous recipients remain needs_clarification, never broadcast or infer authenticated authority from text. Preserve the original inbox/message IDs, frozen source digest and registered bindings. Reconcile-only cancel=true requires evidenced not_called/rejected and ends in cancelled, never reclaimable; unknown cannot cancel. Legacy non-notice inbox sources without frozen packet/attempt/contract context require clarification and explicit cancel/reissue, not invented historical context. Explicit step_id now freezes that delivery context for all modes without changing old business gates. Detailed action-specific API fields are defined in docs/verification/native-gap-next/m1-interface.md; do not invent optional defaults or retry policies.

## M5 grouped transfer and global stall contract

For workflow4 only, inspect board_status.next_action_groups over the existing M1 projection. Handle controls first; no notice-only wakeups. A group shares run_id, recipient, bound agent_id and action_type; each member retains source_type, source_id and source_digest. Call native_action_update(action="claim_group", run_id=..., recipient=..., action_type=..., members=[{source_type,source_id,source_digest},...]). Its group_id and members are individual ledger rows, not a single business receipt.

Call action="begin_group" with group_id and every member's action_id, expected_revision and claim_token, then make one actual native followup_task/send_message against the original target prompting it to read those existing IDs. Record with action="record_group" using the returned member revisions/tokens and real outcome/evidence_ref/evidence_digest/result. Recovery reads native_action_groups (group_id plus full per-action rows); needs_reconciliation members also carry group_id/frozen_member_ids. The complete group membership is mandatory at begin/record/reconcile; one expired member fences all. Frozen membership survives restart; use action="reconcile_group" with group_id, exact member action_id/expected_revision and real host evidence, without old tokens. Outcome/cancel rules remain M1: unknown never replays or cancels; not_called/rejected alone permit retry after revalidation. Failure, control races or changed binding/version stops invocation and requires explicit reconciliation, not partial silent success.

Keep one in-flight business wake per recipient/binding. Respect available native slots and admitted ownership; do not create replacement agents to hide waiting/failure. Each inbox_ack remains per-message with its own version/read/completion evidence. New arrivals remain new projected work outside frozen membership, even while a group is consumed; cursor advancement never proves forwarding or ACK. Retain one inbox_wait per author turn, default20000ms/max25000ms, with no permanent polling.

Use the existing classifier categories ready/completed/inactive/normal_wait/dependency_wait/user_decision/needs_reconciliation/host_unknown/no_progress. Planned potential_candidates still need existing admission; they do not prove executable work. Distinguish normal waiting, dependency not ready, user decision, needs_reconciliation, host state unknown and actual no-progress. Heartbeat expiry requests observation, never proves death. Persist an actionable global alert only for unfinished task + no executable progress + actionable blocker. Root inactivity means waiting for coordinator, not automatic plugin wakeup or zero-token permanent sleep. Treat events as hints; recover remaining IDs from the database after event loss, pause or restart. Respect stopped members and pending controls. Measure actual wakeups/empty waits against M0 before claiming improvement.

## Author: bounded receive, execution and submission

- One inbox_wait call defaults to20000ms, maximum25000ms. Return control on timeout; no permanent polling loop. The coordinator sends from another agent context, never behind the consumer wait in one desktop-agent tool batch.
- Inspect isError and full result before acting. Verify original recipient_agent_id and step_id. Accepted items marked requires_reconciliation must be checked against existing effects before any further action.
- Use inbox_ack(status="accepted") with real read evidence, then action="accept" for the initially dispatched step. Execute only the assigned files. After actual tests and final edits, action="submit". The message's completed receipt means this delivery's requested work was reported, not independent acceptance of the business task.
- On rework, the coordinator returns the exact rejection to the original author and original verifier. action="start_rework" moves rework to implementing; do not call initial accept again. Re-run tests, then submit again. Preserve workspace, native identity and frozen test requirements.
- A paused pending message may be explicitly cancelled with nonempty disposition evidence; cancellation never claims execution or acknowledges a native control request. For uncertain accepted work, reconcile first; do not fabricate completed.

## M2 workflow3 verification collector

Stored workflow3 runs use this collector; stored workflow0/1/2 retain their original semantics and never receive fabricated collector evidence. Older versions reject unsupported command input rather than ignore it. Software0.4.0/schema6 was its historical delivery; workflow4 inherits these collector checks unchanged. The steps below extend, not replace, the candidate/integrated gates and M1 transfer protocol.

1. The original verifier calls artifact_capture before tests with nonempty verification_commands. Freeze each unique id, exact argv string array, absolute existing cwd, finite positive timeout_sec, unique env_keys (names only) and nonempty criteria drawn from the step criteria; collectively cover each criterion. Do not store environment values. env_keys is the exact child environment allowlist, not merely a required-key list. Values come from the verifier terminal; the daemon validates only key syntax/uniqueness and does not require secrets in its environment. The collector checks listed values exist; explicitly list needed SystemRoot/PATH/TEMP and every other required key. Unlisted variables are not inherited; values are never serialized. Capture candidate and integrated separately; retain manifest_path and manifest_digest returned by the backend. The manifest and all logs/test outputs must remain outside captured source scope; changing source requires a fresh capture and checks.
2. Through the host's existing terminal tool and unchanged approval/permissions, the original verifier runs `tri-orchestrator-verify --manifest ABS --output-dir NEW_ABS`, substituting the returned absolute manifest_path and a new absolute output directory that does not exist. Execute exact argv without shell-string composition. No arbitrary command RPC exists; the daemon does not execute tests. Preserve the bounded CLI JSON summary and actual receipt_path, not raw output in chat. Do not overwrite an old run or recreate missing/changed manifests.
3. The original verifier calls verification_record with receipt_files containing the actual absolute receipt path(s), alongside real per-criterion criteria_results and retained evidence_files. Retain actual raw stdout/stderr separately, exit codes, timestamps and output digests; raw command output may contain secrets from the command itself, so inspect its source before sharing it. Environment mappings/values are not serialized or logged by the collector. Backend record and later gate use check the frozen manifest, registered receipt/output evidence chain, current artifact content, binding, packet, attempt and contract. Changed/missing receipts/logs, old attempts or changed source cannot support current PASS.
4. A finished collection or exit0 is not PASS: the verifier must judge each criterion independently. Candidate PASS never substitutes for integrated PASS. Launch failure, timeout, cancellation, collection failure or collector death retains running/incomplete evidence and partial raw output, not fabricated finished. Actual nonzero command exits may be fully collected but still cannot PASS. Windows cleanup is limited to the owned child tree; cleanup failures remain explicit, never a sweep of unrelated processes.

Evidence level local_collector_v1 means local process collection, not host authentication or a signature. Caller agent_id, HTTP self-report and JSON+SHA do not authenticate the original verifier. Pre/post capture and later gate checkpoints cannot detect temporary modification followed by exact restoration between checkpoints; do not claim this limitation is prevented. Preserve original author and original verifier, maximum 3 automatic rework rounds, same-thread FAIL→repair→retest, and M1 claim/begin/record/reconcile for every native review or repair delivery.

## M3 workflow4 plan admission and compact handoff

New runs use workflow4 (software 0.5.0/schema7), inheriting workflow3 collector and workflow2 bindings/mode gates. Stored workflow0/1/2/3 retain their semantics; never backfill new proof or change their dependency rules to escape a deadlock. No public downgrade selector, model override or permission change.

- Freeze execution_kind="native" (default) or execution_kind="coordinator_local" through workflow_step_save before first dispatch. The local kind is allowed only for workflow4 Boost without a workspace, including coordinator-authored investigation reports; it is immutable after original bindings/admission. Register the actual root using the existing coder role, not a new coordinator worker role. On first dispatch and every start_rework, pass agent_id=step["owner_agent_id"] and nonblank evidence of the completed synchronous local edit/verification phase before beginning the next one. This records checkpoint.coordinator_local_boundaries with original identity/action/attempt/evidence; never claim root host idle or fabricate an idle observation while the root is running. Stopped/control/ended-identity, packet, binding, admission and budget checks remain authoritative. These local boundaries apply only to the local step's own dispatch/rework or explicit revision protocol below: delegated native work and predecessor scope reuse still require their real native quiescence. It does not authorize converting a failed native step, skipping independent verification or changing historical workflow contracts.
- To revise already-executed coordinator_local work, first call workflow_step_advance(action="local_revision_boundary", agent_id=step["owner_agent_id"], evidence=completed_phase_evidence, expected_revision=step["revision"]). This requires the original live local owner and completed synchronous phase evidence under the same Boost/no-workspace/stop/control/ended guards. The returned checkpoint.local_revision_boundary is a single-use receipt bound to current revision/packet/contract/attempt and actual project content via content_digest; retain immutable local_revision_boundaries history. The next successful workflow_step_save OR task_packet_save consumes it. Any intervening observation, other workflow revision or filesystem edit invalidates it; read-only queries do not refresh it. task_packet_save consumes the first proof: obtain a fresh local_revision_boundary before workflow_step_save to revise criteria/ownership, using newly read step revisions. For a packet affecting several executed local steps, record a current boundary for each executed local step before saving the packet, then fresh boundaries for their separate step revisions. If packet revision removed an old criterion, boundary creation checks current packet identity without demanding obsolete criterion coverage; revise the step to the new frozen criteria before any normal progress. Preserve original author/verifier/execution_kind/attempt and all native/dependency quiescence gates; neither local revision nor new requirements reset failure history or budget.
- Before dispatch, inspect read-only board_status.plan_readiness: all frozen criteria must be assigned to concrete steps, including project end-to-end requirements. Legal draft steps can be saved incrementally; a readiness hint is not dispatch authorization. Existing atomic workflow_step_advance admission rejects concurrent ownership conflicts. Directory containment, Windows case, conservative glob coverage and path aliases are conflicts unless disjointness is proven; report exact conflicting paths rather than silently narrowing scope or serializing a plan.
- Sequential same-file work needs explicit dependency, current predecessor integrated PASS and confirmed handoff before first admission, plus a real recent native quiescence observation of the prior writer. Heartbeat/dependency completion does not prove it stopped writing. Freeze predecessor packet/contract, original bindings, integrated artifact/verification IDs, handoff and successor allowed scope in the existing checkpoint at first admission.
- After a legitimate successor merge changes predecessor hashes, an already-admitted original author may repair only with the persisted, approved merge-chain proof matching actual artifacts. This historical admission is not current predecessor PASS. Unknown edits, absent merge proof or changed dependency requirements require reconciliation/decision. Recheck controls, original bindings, packet/contract and retained attempt at accept/start_rework; never reset the budget.
- Before final completion or a new successor admission, affected steps need current final PASS from each original verifier on the final integrated artifact. Reopen affected steps with action="reverify"; contradictions need explicit packet revision/reacceptance, not fabricated circular success. Retain each original author workspace and budget until all final gates pass.
- workflow_step_advance(action="handoff", agent_id=current_coordinator_agent_id, recipient_agent_id=next_coordinator_agent_id, next_responsibility=..., forbidden_actions=[...], decision_seqs=[...], evidence=...) creates checkpoint.handoff {pack,digest} and immutable handoff_history. Pack only frozen requirement/milestone/original bindings, artifact/verification references, unresolved inbox/control/native-action IDs, decision seqs, next responsibility and prohibited operations. Read logs by reference, not inside the compact summary.
- The intended recipient reads the exact pack and uses action="ack_handoff", its exact agent_id, handoff_digest=checkpoint["handoff"]["digest"] and actual read evidence. Packet/contract, bindings, artifact/verification refs or unresolved business inbox/control/action membership changes invalidate the old pack; ordinary notices alone do not. Keep immutable history; no arbitrary time expiry or ACK of a recomputed substitute.
- At resume use read-only board_status.resume_context: facts_digest, frozen_packet_id, milestones with original owner/verifier/attempt, artifact_refs, verification_refs, unresolved inbox/controls/native_actions, handoffs with digest/recipient/current/acknowledged, lifecycle_authority and forbidden_actions. Follow referenced artifacts/decisions/unresolved actions; querying never ACKs, claims, dispatches or advances a cursor. Root keeps existing native child lifecycle ownership. A fresh project coordinator receives a plan, not control of old sessions. If an original session is unavailable, preserve the binding and stop at needs_decision; do not impersonate it with a new identity.

Freeze high complexity explicitly with workflow_step_save(complexity="high") before dispatch when a challenger is warranted. workflow_review(step_id,expected_revision,agent_id,criterion,evidence) appends a mapped finding from a registered independent existing worker, distinct from both original author and original verifier, on that high-complexity step. It does not replace original verification or add a resident role. For high-complexity steps original verification_record requires review_dimensions={specification,code,stress,evidence}, each PASS|FAIL|NOT_RUN; high-complexity PASS requires all four PASS (NOT_RUN is not sufficient). Normal-complexity dimensions are optional. Separate code correctness, evidence credibility and final project-goal coverage, not a claim of four independent reviewers. Substantiated findings take original-verifier FAIL → original-author repair. Only actual subsequent PASS by that original verifier may resolve specific findings through resolved_finding_ids; unresolved findings or exhausted budget block completion. An original-verifier actual PASS may use dismissed_finding_ids to dismiss an unsubstantiated finding without increasing attempt; substantiated FAIL cannot be dismissed and requires repaired later-attempt resolved_finding_ids. There is no Success Auditor or second project acceptance state machine.

## M4 evidence-based routing and counterexamples

Use an investigator only for substantive unknowns, then record route_decision in existing board_post(msg_type="info") with packet version, evidence-backed grounds and ownership/dependency boundary. Known local work adds no implementation author. Evidence about actual callers, shared state, reproduction and independent work determines Solo versus delegation; a static check does not prove routing quality.

For difficult frozen scope, the root may use an existing investigator or verifier as a clean-context, read-only challenger. It returns reproducible counterexamples and retained evidence, never edits product source or tests. Proposed test files go to the original author. Register each finding through workflow_review against an existing step and acceptance criterion. The original verifier checks each finding and records actual FAIL through verification_record when substantiated; the original author repairs the same failed step, then the original verifier rechecks it with fresh candidate/integrated evidence. An unresolved finding blocks completion, not merely a recommendation list.

Retain original author, original verifier, workspace and attempt: repairs consume the remaining maximum 3 automatic rework rounds. Scope growth never renames/replaces the failed step or resets its budget. Only genuinely new independent scope gets a new dependent step. A genuinely new requirement needs explicit packet revision and reacceptance; never silently change tests or frozen criteria. Missing responsibility or exhausted budget requires decision rather than replacement identities.

Pure investigation uses the Solo report contract: the investigator stays read-only; the coordinator writes only the approved report artifact and an independent verifier checks it. Do not invent source changes, workspaces or merges. Compare actual failures found and coordination overhead against M0, not role counts; static contracts alone do not prove routing quality.

## Verifier: version-bound candidate and integrated gates

1. Read the actual packet, step and diff; before running independent verification commands call artifact_capture(step_id,scope="candidate"). Workspace candidates use the full approved workspace (no partial paths); Solo can provide explicit source/test paths. Keep test logs outside that captured source scope.
2. Execute actual commands; inspect every frozen criterion. Boost independent challenge evidence uses action="challenge", evidence and the exact verifier agent_id. For workflow2/workflow3/workflow4 pass artifact_id=candidate["id"] from the capture taken before those checks; another artifact/attempt/contract requires a new challenge. Record actual counterexamples/findings, not a promised verdict.
3. Call verification_record(step_id,artifact_id,verifier,verdict,criteria_results,evidence_files,key) with each assigned criterion's actual PASS/FAIL/NOT_RUN and absolute retained evidence paths. Missing or failed criteria cannot yield PASS. Backend rechecks content and evidence; it does not authenticate a claimed process exit code. Never edit source/tests as verifier.
4. A candidate PASS authorizes only the matching candidate. The coordinator performs workspace_merge_preview then workspace_merge. Solo calls action="begin_integrated_review" instead of inventing a merge/workspace.
5. Capture scope="integrated" before running actual final main-directory tests; record integrated verification, then action="complete". After later merges change a completed step's approved scope, action="reverify" explicitly reopens integrated review without resetting the rework budget. A newer packet requires explicit step revision and verification, never inherited PASS.
6. Clean only successfully merged, currently integrated-verified workspaces. Only after every required step is done, packet criteria covered, business inbox work disposed and controls acknowledged may run_update(status="completed") succeed.

## Failure, controls and recovery

- Following the first failed delivery, use at most 3 automatic rework rounds (attempt0 is initial,1..3 are repairs). Duplicate FAIL records never consume another round. At needs_decision, stop automatic dispatch and report the preserved failed evidence; changing names or creating replacement steps is not a budget reset.
- HTTP/MCP write errors are uncertain until persisted state is inspected. Never automatically replay an RPC to obtain inline output or to hide a transport failure.
- A merge stopped between filesystem writes and its database receipt remains integrating/reconciliation_required. Explicit workspace_merge(reconcile=True) checks the existing target; it never reapplies files or commits. Partial/not-applied targets need a human/coordinator decision with the retained staging/backup, not a state-only success.
- Check board_status before/after native waits and at resume. It exposes stored steps, blockers, inbox counts, revisions and observations; summary validity is checked at gate use, not a fresh complete filesystem audit. Keep native state observations separate from registered state and treat observations older than30seconds as stale.
- Teamwork milestone dependencies and confirmed handoff primitives are stored by the same workflow. The root retains native lifecycle ownership; a project coordinator does not take over existing child sessions merely by receiving a plan.

## Mode2 sequencing and delivery binding

- Boost: execute, capture candidate, independent challenge, version-bound candidate verification, original-author repair on FAIL, same-verifier final re-verification, then a separate integrated gate. Solo repairs belong to the coordinator; delegated repairs stay with the original child. Do not replace names, change packets or create a replacement step to evade rework/needs_decision.
- Teamwork: represent each milestone by its existing work step, criteria, dependencies, artifacts and attempt counter. A predecessor must be done with current integrated PASS and confirmed handoff before the dependent implementation is admitted. Recheck dependencies at accept and start_rework. No nested milestone retry budget.
- Handoff: workflow4 additionally uses the M3 immutable pack fields and exact returned handoff_digest for ACK; older versions retain the following recorded primitives. Call action="handoff", agent_id=current_coordinator_agent_id, recipient_agent_id=next_coordinator_agent_id and nonblank evidence after integrated PASS. Only the intended recipient calls action="ack_handoff" with its exact agent_id and actual read receipt. Sending alone is not confirmation. The root retains all native child lifecycle ownership; receiving a plan/checkpoint does not transfer existing child sessions.
- Swarm workflow2 business inbox kinds task/rework/review/result carry the correct step_id, bound recipient and frozen delivery context. task/rework go to the owner; review goes to the verifier; result goes to the owner or verifier of that step. Receipts are independent of step state: receiving, reporting and verification each use their own existing API. Completed delivery never means done work or PASS.
- Each author turn makes at most one bounded inbox_wait (default20000ms/max25000ms), then returns on timeout. The root examines actual native observation before deciding whether to wake an idle/ended original child. A heartbeat timeout alone is never death evidence; pending controls and user stop remain authoritative.
