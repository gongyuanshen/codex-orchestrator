# 0.6.1 会话映射与 Schema 9 隔离验收

- 数据库副本从 Schema 8 升级至 Schema 9，`scripts/upgrade.py prepare → apply → verify` 通过。旧列原值校验通过；新守护进程只用临时数据目录与独立回环端口。
- 三个历史切片都归并到同一个父项目，原 `project_id` 和任务链接保留。旧库只保留了最后一个任务的绑定，因此仅该任务以 `#1` 显示在真实 Codex 会话下；其余两个进入「未绑定会话任务」。不按路径、标题或时间猜测缺失绑定。
- 本次没有升级生产数据、改写 Codex 配置或访问生产守护进程。`verify` 只验证隔离后端，不代表 Codex 正式安装或 MCP 热重载。

- 最终全量回归：898 通过、2 跳过、0 失败。默认跳过的真机 T7 已单独复验通过，另一项是 Windows 不适用的 POSIX 进程组测试。

## 复验

### 验收范围与延期项

- 本地交付不以 Codex 模型额度为前提。原 S3 要求的真实 Codex 原生派发、候选/集成回执和 `workflow_closeout_run` 已暂缓，状态不是通过。
- 另用合成任务实际运行了 `tri-orchestrator-verify` 的候选、集成两阶段，并通过 `workflow_closeout_run` 检查收尾。该用例的原生代理响应来自夹具，不作为正式 Codex 回执。
- 隔离安装、Hook 信任及 MCP 生命周期验证通过。生产安装、生产 MCP 重连和部署不属于此次本地交付。

`python -m pytest -q tests/test_s4_upgrade_t7.py` 默认只运行合成 Schema 8 WAL 夹具，不接触本机运行库。

真机用例须显式设置以下环境变量，并将任何 `--basetemp` 参数指向一个全新的临时目录：

| 变量 | 说明 |
| --- | --- |
| `TRI_ORCH_T7_STATE_DB` | Schema 8 数据库的绝对路径。用例只读取数据库和 WAL 的字节，校验副本后才在临时目录中调用 SQLite 备份。 |
| `TRI_ORCH_T7_CODEX_HOME` | 用于只读核实项目和会话名称的 Codex 数据目录。 |
| `TRI_ORCH_T7_BASELINE_REF` | 本仓库中对应 `0.6.0/schema8` 的提交；旧插件从该提交导出至临时目录。 |
| `TRI_ORCH_T7_EXPECTATIONS` | 仓库外的 UTF-8 JSON 文件，记录本机需要检查的父项目、会话和切片。 |

场景 JSON 格式（示意）：

```json
{
  "project_id": "proj_parent",
  "project_name": "父项目展示名",
  "session_id": "Codex根会话ID",
  "session_name": "Codex会话展示名",
  "runs": {"run_a": "proj_slice_a", "run_b": "proj_slice_b", "run_c": "proj_slice_c"}
}
```

然后执行：

```powershell
.\.venv\Scripts\python.exe -m pytest -q -s tests/test_s4_upgrade_t7.py::test_real_machine_snapshot_upgrade
```

如果副本仍有活跃任务，或快照采集期间源文件发生变化，演练会停止，不应绕过升级门禁。不要提交数据库、WAL、场景 JSON、临时升级回执或原始日志。
