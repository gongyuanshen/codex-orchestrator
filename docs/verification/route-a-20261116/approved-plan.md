# 路线 A 开发计划：可靠编排基础与三模式增强

## 一、目标与已确定的边界

**目标：**保留现有 Codex 原生子代理，把消息投递、验收、返工和恢复从主要依赖提示词，升级为有持久记录、后端门禁和真实执行证据的流程。

**架构：**继续使用现有 Python、SQLite、HTTP/SSE、MCP 和隔离工作区。根协调者调用 Codex 原生工具；插件负责保存状态、检查条件和展示结果，不自行接管桌面会话。

已确定：
- 按“共同基础 → 隔离实测 → 更新安装版 → 各模式增强”分批交付。:codex-annotation{index="1"}
- 保留 **18790** 和 `/boost`、`/teamwork`、`/swarm` 三个入口。
- 首次交付失败后，每个工作项最多自动返工 **3 轮**；仍失败则进入“待用户决策”，不标记完成。里程碑沿用所属工作项的次数，不另套循环放大次数。
- 不新增消息队列、第二个调度服务或路线 B 的自管会话。
- 开发和测试不修改生产任务；需要界面操作时由用户完成。
- 原有暂停、终止要求优先，返工和恢复不得自动重新启动被用户停止的代理。

## 二、共同基础与接口合同

### 1. 正式收件箱

将已验证原型纳入正式插件，复用现有数据库事务、消息板和 EventBus，不导入原型测试数据。

保留四个接口：`inbox_send`、`inbox_get`、`inbox_ack`、`inbox_wait`。

固定行为：
- 相同幂等键与内容返回原消息；同键不同内容明确冲突。
- 消息与对应消息板记录同事务提交。
- 默认等待 20 秒，最大 25 秒；等待走异步路径，不占用长期线程池任务。
- 断连、取消和服务退出必须清理等待与订阅；错误不得包装成普通超时。
- 已接收但未完成的工作标记为“需要核对”，不自动重放。
- 投递时保存对应的原生代理绑定；代理被替换后，旧消息不得静默转交给新代理。
- 固定使用“协调者发送、另一个代理等待”；不依赖已失败的同代理并发等待／发送方式。

### 2. 结构化步骤、验收与检查点

在现有任务包、工作区和控制请求上增加：
- 不可由普通 RPC 降级的运行流程版本。
- 工作步骤记录：负责人、验收者、任务包版本、依赖、阶段、返工次数、修订号和恢复检查点。
- 不可变追加的验收记录，区分“候选交付验收”和“合入后集成验收”。

新增最小接口组：
- `workflow_step_save`：创建或修订步骤及依赖。
- `workflow_step_advance`：按允许的动作推进阶段，要求 `expected_revision`。
- `artifact_capture`：由后端生成交付物清单和摘要。
- `verification_record`：记录对应版本、产物、验收项和证据。
- 现有 `board_status`、任务详情和报告接口增加上述状态，不再建立平行查询体系。

**有效 PASS 必须同时满足：**
- 对应当前任务包、工作项、交付版本和验收者绑定。
- 验收者与作者不同；验收项无缺失、失败或未执行。
- 证据文件存在且摘要匹配。
- 验收前后交付物一致，使用时仍匹配当前产物。
- 候选 PASS 不代替集成 PASS；代码、测试或需求改变后重新验收。

当前为可信本机协作：这些检查保证记录和流程一致性，不把调用者提交的身份或退出码宣称为宿主认证证明。

### 3. 后端门禁与合入恢复

门禁放在共享数据库／工作区服务层，HTTP、MCP、界面和内部调用均须经过：
- 新流程任务只能从活动状态创建，不能直接创建为完成。
- 合入前必须存在匹配实际候选产物的 PASS。
- 完成前必须通过集成验收，且没有未处置任务、待执行控制、不确定合入或未完成交接。
- 普通通知未读不阻塞完成；任务类消息及已接收的不确定动作必须处置。
- 自由文本“PASS”、成员状态或任意 metadata 不能替代验收记录。
- 集成失败保留原作者工作区，不提前清理。

产物绑定：
- Git 使用实际取回并准备合入的不可变提交。
- Snapshot 与 Solo 使用明确范围的文件清单和内容摘要，包含新增、修改与删除。
- Snapshot 合入前固定已验收内容，持久化合入操作与目标原状；逐文件应用后读回核对。
- 中途退出进入“需要核对”，不得自动重复合入、清理工作区或宣称完成。复用现有三方比较处理恢复，不声称文件系统和 SQLite 构成整体原子事务。

## 三、分批实施与独立验收

### 第一批：共同基础正式落地

- [ ] **存储与兼容：**完成增量迁移、收件箱、步骤／验收记录、修订冲突检查和恢复检查点。
- [ ] **传输与生命周期：**正式 RPC 接入异步等待，统一 MCP／HTTP 工具目录，复用现有启动器和错误处理。
- [ ] **验收与合入门禁：**封堵直接完成、直接合入、旧 PASS 复用和未验收清理；补齐 Snapshot 中断恢复。
- [ ] **协调者接入：**同步修改三个技能、角色指令、内联角色契约和调用示例，统一收件、原生转交、回执、返工及恢复流程。
- [ ] **界面接入：**保持现有简洁布局，仅增加当前阶段、阻塞原因、返工次数和恢复提示；区分“登记状态”“最近观察到的宿主状态”“信息已过期”。
- [ ] **安装包验收与上线：**完成隔离安装测试后，进行第一次受控更新。

第一批每项均执行“失败测试 → 最小实现 → 回归 → 独立审查”，不得用整批一次性修改代替逐项验证。

### 第二批：三个模式专项增强

**Boost**
- 增加结构化“执行 → 独立挑战 → 原作者修正 → 最终复验”阶段。
- 复用现有调查者和验收者，记录反例与检查结果，不先扩充一套新角色。
- Solo 由协调者修复；委派路径交原作者修复；保持同一验收者复验。
- 按已确定的 3 轮规则收尾。

**Teamwork**
- 增加多里程碑、依赖、阶段准入和交接确认。
- 前置里程碑未通过，不启动依赖它的实施阶段。
- 每个里程碑保留候选验收、集成验收、产物版本和未决事项。
- 根协调者始终持有原生调度职责；新的项目协调者只接收计划和检查点，不假定可以接管原有子代理。
- 交接必须由接手方确认，发送交接消息本身不算完成。

**Swarm**
- 将任务分派、收件、执行、验收和返工统一关联到工作步骤。
- 子代理单次有界等待结束后返回控制，不无限循环等待。
- 已结束代理由根协调者检查状态后调用原生唤醒；心跳超时只表示需要检查，不直接当作代理死亡。
- 保持任务概览优先，长日志继续折叠，新增状态不得重新堆满首页。

第二批同样先隔离验收，再进行独立的安装版更新，不与第一批一次性捆绑上线。

## 四、测试与验收标准

### 自动化回归

- 收件：重复投递、内容冲突、错误收件人、代理换绑、关闭任务。
- 等待：空队列、25 秒边界、多等待者、事件丢失、取消与服务退出清理。
- 门禁：直接创建 completed、绕过 UI 调用合入、缺验收项、伪造普通 PASS 文本、证据缺失。
- 失效：验收后改代码／测试／任务包，旧 PASS 不再授权合入或完成。
- 返工：原作者与原验收者复用；重复失败回执不重复计数；3 轮后明确待决策。
- 恢复：接收后退出、执行后回执前退出、合入中断、文件已应用但数据库未提交。
- 兼容：历史任务、旧工作区、未来数据库版本拒绝、新客户端误连旧服务。
- 界面：三个入口只显示对应模式，阻塞与过期状态准确，长内容不撑开概览。

### 真实原生代理验收

分别完整运行：
1. Boost Solo 与委派路径。
2. Teamwork 至少两个有依赖的里程碑及一次交接。
3. Swarm 多成员并行和跨代理消息投递。

每条路径均包含真实验收失败、原作者返工、同一验收者复验和最终集成检查；另测返工耗尽、人工停止与服务恢复。判定依据是实际命令和产物，不是要求代理输出 PASS。

安装验收必须从隔离安装包启动，不能依赖开发目录或原型模块；同时验证中文／空格路径、单例启动及大结果文件交付。

## 五、兼容、发布与回退

- 历史任务保留原样，标明“旧流程，未启用结构化门禁”，不补造 PASS。新任务自动采用当前流程版本，普通接口不得选择旧版绕过门禁。
- 健康接口增加软件版本、数据库版本和能力标识。新客户端遇到旧服务时明确提示需要切换，不自行重启生产服务。
- 数据库在任何迁移前拒绝高于程序支持范围的版本。
- 每次上线先确认 **所有模式**均无活动任务；有活动任务则延期，不强制结束。
- 使用受控升级入口：停接新任务、备份程序包与一致性数据库、停止旧服务、安装迁移、读回校验，再开放新任务；不直接执行现有“先卸载再安装”的热更新路径。
- 未恢复真实生产写入前，可以回退程序包与配套快照；新版已产生数据后，保留数据并前向修复，不用旧快照覆盖。
- 必要的 MCP 刷新由用户操作，并以新宿主客户端的实际工具调用验收，不假定旧聊天会热刷新。
- 同步更新版本元数据、工具说明和验证记录；本计划不包含公开发布 GitHub Release。

**计划边界：**本轮未修改文件、执行迁移或安装更新。路线 A 不承诺后台独立调度、永久零开销等待、旧主对话热重连或与原生运行时完全等价。
